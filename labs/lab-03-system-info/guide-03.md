# Лабораторная работа 3. Порядок выполнения

Все команды — в обычном терминале ВМ, root не нужен. Работает одинаково в Server и в Desktop.

---

## Шаг 1. Ядро

**Что это.** `uname` печатает то, что знает о себе само ядро: имя, версию, архитектуру (см. «Теоретические сведения» в задании).

```bash
uname -a
```

**Ожидаемый результат:** одна строка вида `Linux <хост> 6.8.0-<N>-generic #<N>~... x86_64 ... GNU/Linux`. Номер версии ядра у вас будет свой — это нормально, у всех разный.

📷 Сделайте снимок вывода.

**Если не получилось:** команда есть в любом Linux без установки пакетов; если оболочка пишет `command not found`, проверьте, что не опечатались (`uname`, не `unname`/`uname-a`).

## Шаг 2. Дистрибутив

```bash
cat /etc/os-release
```

**Ожидаемый результат:** несколько строк вида `NAME="Ubuntu"`, `VERSION="24.04...`. Сравните с выводом шага 1 — это не одно и то же: `uname` показывает ядро, `os-release` — дистрибутив (объяснение — в «Теоретических сведениях»).

📷 Снимок.

**Контрольная точка.** У вас должно быть два *разных* по содержанию вывода: один про ядро, другой про дистрибутив. Если `/etc/os-release` пустой или файла нет — вы не в Ubuntu/Debian-подобной системе, сообщите преподавателю.

## Шаг 3. Процессор — сводка

```bash
lscpu
```

**Ожидаемый результат:** таблица полей. Найдите и выпишите: `CPU(s)`, `Core(s) per socket`, `Thread(s) per core`, `Model name`. *Числа зависят от вашей машины (и от того, сколько ядер выделено ВМ) — у всех будут свои, это не ошибка.*

**Если не получилось:** `lscpu: command not found` — на минимальной установке Server пакет `util-linux` иногда всё же отсутствует; поставьте `sudo apt install -y util-linux`.

## Шаг 4. Процессор — сырые данные

**Что это.** `lscpu` не выдумывает числа — он читает `/proc/cpuinfo`, файл, который ядро отдаёт по запросу (подробнее о том, что такое файлы `/proc`, — лекция 4).

```bash
less /proc/cpuinfo
```

Пролистайте (`Space` — вперёд, `q` — выход), найдите строку `model name` и сравните с `Model name` из `lscpu` — они совпадают. Затем посчитайте число блоков `processor`:

```bash
grep -c ^processor /proc/cpuinfo
```

**Ожидаемый результат:** число совпадает с `CPU(s)` из шага 3.

📷 Снимок команды `grep -c ^processor /proc/cpuinfo` с результатом.

**Если не получилось:** число не совпало — проверьте, что в `grep` есть `^` (иначе считаются и другие строки, где слово `processor` встречается не в начале, например внутри `vendor_id`... на практике на x86 такого нет, но привычку ставить `^` при поиске по началу строки полезно закрепить).

**Контрольная точка (после шагов 1–4).** У вас должно быть: одна строка про ядро, несколько строк про дистрибутив, таблица `lscpu` и подтверждение, что число процессоров и модель в `lscpu` и в `/proc/cpuinfo` — одно и то же.

## Шаг 5. Память — сводка

```bash
free -h
```

**Ожидаемый результат:** три строки (`Mem`, `Swap` и в некоторых версиях `total` отдельно), столбцы `total`, `used`, `free`, `shared`, `buff/cache`, `available`. Обратите внимание на разницу `free` и `available` — она объяснена в «Теоретических сведениях» задания; почти всегда `available` заметно больше `free`, и это нормально, а не нехватка памяти.

📷 Снимок.

## Шаг 6. Память — сырые данные

```bash
head -5 /proc/meminfo
```

**Ожидаемый результат:** строки `MemTotal`, `MemFree`, `MemAvailable` (и, возможно, ещё одна) в килобайтах. Переведите вручную в гибибайты (делением на 1024² или прикидкой) и сравните с `free -h` из шага 5 — с точностью до округления числа должны совпасть.

**Если не получилось:** числа сильно разошлись — проверьте, что вы не путаете КБ (`/proc/meminfo`) с ГиБ (`free -h`): `free -h` уже делит на 1024² сама.

## Шаг 7. Загрузка системы

```bash
uptime
nproc
```

**Ожидаемый результат:** `uptime` — время непрерывной работы и три числа load average (1, 5, 15 минут); `nproc` — число доступных ядер. Сравните наибольшее из трёх чисел load average с результатом `nproc`.

*Если ВМ всё это время простаивала, все три числа load average будут около `0.00` — это ожидаемо, а не ошибка: значит, процессам не приходится ждать очереди.*

📷 Снимок обеих команд.

## Шаг 8. Процессы

```bash
ps aux | wc -l
```

Число строк на 1 больше числа процессов — первая строка это заголовок таблицы (`USER PID %CPU ...`), вычтите её при подсчёте.

```bash
ps aux --sort=-%mem | head -6
```

**Ожидаемый результат:** первая содержательная строка после заголовка — процесс с наибольшим `%MEM`. Запишите его `COMMAND`, `VSZ`, `RSS`.

📷 Снимок обеих команд.

**Если не получилось:** `ps: unrecognized option '--sort'` — редкий случай нестандартного `ps`; используйте `ps aux | sort -k4 -rn | head -6` (сортировка по 4-му столбцу, `%MEM`, в обратном порядке).

## Шаг 9. Дерево процессов

```bash
pstree -p
```

**Ожидаемый результат:** дерево процессов от `systemd` (или `init`) с PID 1. Найдите в дереве свою `bash` и запишите, какой процесс — её родитель (обычно это ваш `sshd`, `login` или графический терминал — зависит от того, как вы подключены к ВМ).

**Если не получилось:** `pstree: command not found` — пакет `psmisc` отсутствует: `sudo apt install -y psmisc`.

**Контрольная точка (после шагов 5–9).** У вас заполнены все восемь пунктов части 1 задания с реальными числами со своей машины.

## Часть 2. Как искать значение своего поля

Для вашего варианта нужно объяснить одно поле `/proc/cpuinfo`, одно поле `/proc/meminfo` и один столбец `ps aux`, которых не было в шагах 1–9. Официальное описание всех полей — в системной справке:

```bash
man 5 proc
```

Это длинная страница; открыв её, нажмите `/`, наберите название своего поля (например `/MemAvailable` или `/cache_alignment`) и `Enter` — курсор перейдёт к описанию. Для столбцов `ps aux`, включая расшифровку всех кодов `STAT`, — `man ps`, раздел `PROCESS STATE CODES`.

## Задача со звёздочкой: как оформить сценарий (необязательно)

Если делаете `system-report.sh`, файл создаётся и запускается так же, как в ЛР 1–2 работали с текстовыми файлами, плюс два новых шага:

```bash
nano system-report.sh
```

Первая строка файла — `#!/bin/bash` (говорит системе, каким интерпретатором запускать файл), дальше — обычные команды, как в задании. Сохраните (`Ctrl+O`, `Enter`, `Ctrl+X`), затем:

```bash
chmod +x system-report.sh
./system-report.sh
```

**Если не получилось:** `Permission denied` — не выполнен `chmod +x`; `command not found` при запуске `system-report.sh` без `./` — в текущем каталоге команды ищутся, только если он есть в `PATH` (лекция 2), поэтому явное `./` обязательно.

## Типичные ошибки

| Симптом | Причина | Что делать |
|---|---|---|
| `lscpu`/`free`/`pstree`: command not found | не установлен нужный пакет (`util-linux`, `procps`, `psmisc`) | `sudo apt install -y <пакет>` |
| `/etc/os-release` пустой или отсутствует | не Ubuntu/Debian-подобная система | сверить с `lsb_release -a` как запасной вариант |
| число из `grep -c ^processor` не совпало с `CPU(s)` | забыли `^` в `grep`, посчитались лишние строки | повторить с `grep -c ^processor` |
| `ps aux \| wc -l` — число «на один больше, чем ожидали» | не вычли строку заголовка | вычесть 1 или использовать `ps aux --no-headers \| wc -l` |
| `pstree` без PID | забыт флаг `-p` | `pstree -p` |
| load average кажется «слишком большим» на слабом ноутбуке | фоновые обновления/другие программы хоста грузят ВМ | это наблюдение, а не ошибка — описать в отчёте как есть |
| в отчёте написано «памяти не хватает», потому что `free` маленький | перепутаны `free` и `available` | перечитать объяснение в «Теоретических сведениях», использовать `available` |
| `./system-report.sh: Permission denied` | не выполнен `chmod +x` | `chmod +x system-report.sh` |
| числа `/proc/meminfo` «не сходятся» с `free -h` | не переведены единицы (КБ vs ГиБ) | пересчитать вручную, `free -h` уже делит на 1024² |
