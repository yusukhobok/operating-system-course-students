# Лабораторная работа 7. Порядок выполнения

Вы сравните три реакции на сигнал: завершиться, выполнить обработчик и отложить обработку. Затем проверите, кому терминал посылает `Ctrl+C`.

Работайте в одном терминале ВМ без `sudo`. Обозначения `<...>` заменяйте своими значениями, без скобок. Откройте [задание](task-07.md): нужны четыре сигнала для шага 1 и числа `K`, `m`, `M`, сигнал `s` для исследования. PID и время у вас будут своими.

# Часть 1. Наблюдение

Эта часть нужна для отчёта по лабораторной, но не переносится в РГР.

## Шаг 1. Узнайте имена и номера сигналов

**Сигнал** сообщает процессу о событии. У каждого сигнала есть имя и номер. Подробнее — лекция 6, разделы 6.5–6.6.

```bash
kill -l
kill -l 10
kill -l SIGUSR1
```

На x86 в учебной ВМ последние две команды показывают `USR1` и `10`: перевод из номера в имя и обратно.

Для каждого из четырёх сигналов своего варианта повторите следующий опыт, заменяя `<сигнал>`:

```bash
sleep 100 &
P=$!
kill -<сигнал> $P
wait $P
echo $?
```

`P=$!` сохраняет PID фонового запуска, `wait` дожидается именно его. Считывайте `$?` сразу после `wait`.

Bash обозначает завершение сигналом `n` числом `128 + n`. Например, для `TERM` с номером 15 получается 143. Служебные сообщения `Terminated`, `Killed` не являются отдельными ошибками опыта.

📷 Сохраните четыре результата. Сделайте таблицу «сигнал — номер — результат `echo $?`».

**Если не получилось:** `No such process` — повторите запуск. Если сигнал не завершил процесс, проверьте имя и его действие в таблице задания.

## Шаг 2. Проверьте клавиши терминала

Запустите:

```bash
sleep 100
```

Нажмите `Ctrl+C`, затем выполните `echo $?`. Повторите с новым `sleep 100` и `Ctrl+\`, затем ещё раз — с `Ctrl+Z`.

| Клавиши | Сигнал | Что проверить |
|---|---|---|
| `Ctrl+C` | `INT` | процесс завершился |
| `Ctrl+\` | `QUIT` | процесс завершился; возможно сообщение о дампе |
| `Ctrl+Z` | `TSTP` | процесс остановлен, но ещё существует |

После `Ctrl+Z` посмотрите `jobs`, затем верните процесс командой `fg` и завершите `Ctrl+C`. Не оставляйте остановленный процесс к следующему шагу.

Код после остановки — не доказательство завершения: смотрите также сообщение оболочки и `jobs`.

📷 Сохраните три результата `echo $?` и состояние остановленного задания.

**Если не получилось:** команда должна работать на переднем плане, без `&`. Если она в фоне, сначала выполните `fg`.

## Шаг 3. Прочитайте маски сигналов

Маска — число, в котором каждый бит отвечает за один сигнал. В файле `status` числа записаны в шестнадцатеричной форме.

```bash
sleep 300 &
P=$!
grep -E 'SigBlk|SigIgn|SigCgt|ShdPnd' /proc/$P/status
grep -E 'SigBlk|SigIgn|SigCgt|ShdPnd' /proc/$$/status
kill -TERM $P
wait $P
```

`$$` — PID вашей оболочки. Сравните её маски с масками `sleep`:

| Поле | Значение |
|---|---|
| `SigBlk` | обработка каких сигналов заблокирована |
| `SigIgn` | какие сигналы игнорируются |
| `SigCgt` | для каких сигналов установлены обработчики |
| `ShdPnd` | какие сигналы ожидают доставки процессу |

Правило чтения: **сигналу с номером `n` соответствует бит `n − 1`**. Биты считаются с нуля. Для сигнала 10 нужен бит 9, для сигнала 15 — бит 14.

Чтобы получить шестнадцатеричное значение одного бита, выполните:

```bash
printf '%x\n' $((1 << (10-1)))
printf '%x\n' $((1 << (15-1)))
```

Получатся `200` и `4000`. `1 << ...` сдвигает единственную единицу на нужное место, `%x` печатает число в шестнадцатеричной форме. Для нескольких разных сигналов складывают значения их битов. Нули слева можно не учитывать.

Маски `sleep` и оболочки зависят от способа запуска. Не копируйте чужие числа: расшифруйте свой `SigCgt` по таблице задания.

📷 Сохраните обе группы полей и свою расшифровку.

**Проверьте часть 1.** Вы различаете остановку и завершение и можете перевести бит маски в номер сигнала.

# Часть 2. Исследование: обработка и блокировка сигналов

**Эта часть позже станет разделом 4 РГР. Опыты повторять не нужно.** Используйте `wcstat` и свой `data.txt` из ЛР 4.

У программы есть обработчики `INT`, `TERM`, `USR1`, `CHLD`. Ключ `-m` временно блокирует доставку `INT`, `TERM`, `USR1`: сигнал может прийти сейчас, но обработчик выполнится позже. Это отличается от игнорирования, при котором сигнал отбрасывается.

## Шаг 4. Запишите прогноз и посмотрите обработчики

```bash
cd ~/<фамилия>/rgr/programs
ls -l wcstat data.txt
```

Если программы нет, выполните `make`; файл восстановите по [гайду ЛР 4](../lab-04-syscalls/guide-04.md), шаг 6.

**До опытов** запишите прогнозы из задания: маски родителя и потомка; число уведомлений при `m` посылках с паузами и при блокировке; реакцию потомка `M` на `s`; реакцию на `Ctrl+C`; возможное число `SIGCHLD`.

Запустите программу с паузой после каждого блока:

```bash
./wcstat -p <K> -c -b 4096 -s 150 data.txt > masks.txt &
P=$!
sleep 1
ps -o pid,ppid,comm --ppid $P
```

Возьмите PID одного потомка из списка:

```bash
C=<PID>
grep -E 'SigBlk|SigIgn|SigCgt|ShdPnd' /proc/$P/status
grep -E 'SigBlk|SigIgn|SigCgt|ShdPnd' /proc/$C/status
kill -TERM $P
wait $P
```

Сравните `SigCgt` родителя и потомка и расшифруйте его. Потомок наследует обработчики при создании через `fork`.

📷 Сохраните обе группы масок и подпишите сигналы.

## Шаг 5. Сравните доставку с блокировкой и без неё

Сначала обычный запуск:

```bash
./wcstat -p <K> -c -b 4096 -s 150 data.txt > normal.txt &
P=$!
sleep 1
```

Отправьте свой сигнал `USR1` ровно `m` раз с паузами. В `seq` подставьте своё `m`:

```bash
for i in $(seq 1 <m>); do
    kill -USR1 $P
    sleep 0.3
done
wait $P
cat normal.txt
```

Повторите с `-m`, без пауз между посылками:

```bash
./wcstat -p <K> -m -c -b 4096 -s 150 data.txt > blocked.txt &
P=$!
sleep 1
for i in $(seq 1 <m>); do
    kill -USR1 $P
done
grep -E 'SigBlk|ShdPnd' /proc/$P/status
wait $P
cat blocked.txt
```

Цикл повторяет команду заданное число раз. Без блокировки ищите отдельные уведомления; при блокировке — сначала ожидающий бит, затем обработку после разблокировки. Обычные одинаковые сигналы могут объединяться: они не образуют счётчик всех отправок.

📷 Сохраните уведомления обоих запусков, `SigBlk`, `ShdPnd` и итог. Сравните с прогнозом; отдельно запишите число `SIGCHLD`.

**Если не получилось:** программа завершилась до посылок — повторите с большей паузой, например `-s 500`, и укажите изменение. Если без `-m` уведомлений меньше `m`, проверьте паузы и фактическое время работы.

## Шаг 6. Пошлите сигнал одному потомку

```bash
./wcstat -p <K> -c -b 4096 -s 150 data.txt > child-signal.txt &
P=$!
sleep 1
cat child-signal.txt
```

В начале файла найдите строку «потомок M, PID …» со своим номером `M`. Не выбирайте потомка по порядку вывода `ps`.

```bash
C=<PID>
kill -<s> $C
wait $P
echo $?
cat child-signal.txt
wc data.txt
```

Запишите, завершился ли потомок сам после обработчика или был убит сигналом. Сравните итог с `wc`: он может быть неполным, если потомок не закончил свою часть. Нулевой код родителя сам по себе не гарантирует полноту результата.

📷 Сохраните сообщение о выбранном потомке, итог и код родителя. Причину реакции объясните по таблице сигналов задания.

## Шаг 7. Пошлите `Ctrl+C` всей группе

Запустите **без `&` и без перенаправления**:

```bash
./wcstat -p <K> -c -b 4096 -s 150 data.txt
```

Через пару секунд нажмите `Ctrl+C`, после возврата приглашения выполните:

```bash
echo $?
```

Ищите сообщения об остановке родителя и потомков, статусы потомков и частичный итог. Терминал посылает `INT` всей группе процессов переднего плана. Команда `kill -TERM $P` из предыдущих шагов адресовала сигнал только одному процессу; дальнейшая остановка потомков зависела от самой программы.

📷 Сохраните результат и объясните различие двух способов остановки.

## Типичные ошибки

| Что произошло | Что сделать |
|---|---|
| Нет `wcstat` или файла | Проверьте `rgr/programs`, сборку `make` и файл из ЛР 4 |
| `kill`: `No such process` | Программа закончилась; повторите с большей паузой |
| `ShdPnd` нулевой | Смотрите во время работы с `-m`, сразу после посылок |
| Уведомлений меньше отправок | Проверьте паузы; обычные сигналы могут объединяться |
| Выбран не тот потомок | Возьмите PID из строки программы с номером `M` |
| Перепутаны биты маски | Бит 0 — сигнал 1; бит 9 — сигнал 10 |
| `Ctrl+C` не действует на опыт | Запустите программу на переднем плане, без `&` |
| После `Ctrl+Z` остался `sleep` | `fg`, затем `Ctrl+C` |
| Итог неполный, но код родителя 0 | Зафиксируйте оба наблюдения: программа не проверяет полноту автоматически |
| Маски отличаются от примера | Расшифруйте свои значения; способ запуска влияет на наследование |
