## Теоретические сведения

**Системный вызов** (system call) — обращение программы к ядру за услугой: открыть файл, прочитать данные, создать процесс. Программа не может сама прочитать диск или вывести символ на экран — это умеет только ядро, работающее в режиме ядра. Поэтому за каждым таким действием стоит системный вызов: процессор переходит в режим ядра, ядро проверяет аргументы и права, выполняет работу и возвращает результат (лекция 4, раздел 4.5).

**Системный вызов и библиотечная функция.** В программе на C системный вызов выглядит как обычная функция: `read(fd, buf, 100)`. Но функции библиотеки C делятся на два вида. Одни — тонкие обёртки над системными вызовами: `open`, `read`, `write`, `close`; их справка — в разделе 2 (`man 2 write`). Другие — обычные функции, выполняются в режиме пользователя и только иногда обращаются к ядру: `printf` копит текст и в какой-то момент вызывает `write`, а `strlen` к ядру не обращается вообще; их справка — в разделе 3 (`man 3 printf`). Команда `man -f имя` показывает, в каких разделах есть страница.

**`strace`** запускает программу и печатает каждый её системный вызов: имя, аргументы и результат после знака `=`. Например

```
openat(AT_FDCWD, "/etc/hostname", O_RDONLY) = 3
read(3, "myhost\n", 131072)             = 7
write(1, "myhost\n", 7)                 = 7
```

читается так: открыт файл `/etc/hostname` только на чтение, ядро выдало файловый дескриптор 3; из дескриптора 3 прочитано 7 байт (просили до 131072); 7 байт записано в дескриптор 1 — стандартный вывод. Функция `open` из библиотеки C вызывает системный вызов `openat` (в старых системах — `open`), поэтому в `strace` он называется так. Ключ `-c` вместо списка печатает таблицу: сколько раз вызван каждый системный вызов (`calls`), сколько из них завершились ошибкой (`errors`) и сколько времени они заняли.

**Первые строки любого `strace`** — это не сама программа, а её запуск: `execve` загружает программу, затем загружается библиотека C (`openat` файла `libc.so.6`, несколько `mmap`), настраивается локаль (`openat` файлов в `/usr/lib/locale`). Работа программы — в конце вывода. Ошибки в начале (`ENOENT` при поиске файлов локали, `ENOTTY` у `ioctl`) — нормальная часть запуска: библиотека проверяет, есть ли файл или терминал, и действует по результату.

**Ошибки.** При ошибке системный вызов возвращает `-1`, а код причины записывается в переменную `errno` (лекция 4, раздел 4.6). В `strace` это видно сразу: `= -1 ENOENT (No such file or directory)`. Частые коды: `ENOENT` (2) — нет такого файла или каталога; `EACCES` (13) — нет прав доступа к файлу или каталогу; `EPERM` (1) — операция разрешена только владельцу или root; `EEXIST` (17) — уже существует; `EISDIR` (21) — это каталог; `ENOTDIR` (20) — часть пути не каталог; `ENOTEMPTY` (39) — каталог не пуст. Программа печатает текст ошибки функцией `perror` и завершается с ненулевым кодом, который оболочка показывает командой `echo $?`. Число кода можно найти в заголовочном файле: `grep -hw EACCES /usr/include/asm-generic/errno*.h`. Какие коды может вернуть именно этот вызов и при каких условиях — раздел ERRORS в его справке (`man 2 mkdir`).

**Стоимость системного вызова.** Переход в режим ядра и обратно, сохранение регистров, проверка аргументов стоят в десятки–сотни раз дороже обычного вызова функции (лекция 4, раздел 4.5). Поэтому важно, **сколько** системных вызовов делает программа. Программа, которая читает файл размером `S` байт блоками по `B` байт, обращается к ядру `⌈S / B⌉` раз (деление с округлением вверх): чем меньше блок, тем больше вызовов. Если читать «до конца файла» вызовом `read`, понадобится ещё один — последний вернёт 0, «конец файла». Время, которое программа провела в ядре, показывает команда `time` в строке `sys`, время в режиме пользователя — в строке `user`.

**Буферизация `printf`.** `printf` не вызывает `write` на каждую строку. Библиотека C копит вывод в буфере внутри процесса и отдаёт ядру одним `write`. Когда стандартный вывод — терминал, буфер сбрасывается после каждого `\n`, чтобы человек сразу видел строку. Когда вывод перенаправлен в файл, буфер сбрасывается, только когда заполнится (4096 байт) или программа завершится. Поэтому одна и та же программа делает разное число системных вызовов в зависимости от того, куда идёт её вывод (лекция 4, раздел 4.5; подробно — лекция 6, раздел 6.5). Готовая программа `lines` печатает заданное число строк либо через `printf`, либо прямо системным вызовом `write` — и это можно сравнить.

**Готовая программа части 1** — `lines` — лежит в каталоге `programs/` работы, собирается командой `make`. Изменять её не нужно, но прочитать полезно: она короче 30 строк, системные вызовы в ней и в `wcstat` описаны в мини-справочнике `handouts/syscalls-04.md`.

|---|---|---|

Она читает файл блоками, и размер блока выбирает «на глаз»: слишком малый — слишком много системных вызовов, слишком большой — лишняя память. А иногда команда вообще завершается ошибкой, и нужно быстро понять, какой системный вызов отказал и почему. Нужно выяснить на вашей машине, как размер блока влияет на число системных вызовов и время работы сквозной программы РГР `wcstat`, во что обходится один системный вызов и по какому условию ядро выбрало тот код ошибки, который вернуло.

**Прогноз (до запуска; записывается в отчёт).**
1. Размер `S` файла `data.txt` в байтах (`ls -l`) и число блоков (= числу вызовов `pread` с данными) для каждого из пяти размеров блока: `⌈S / блок⌉`.
2. Во сколько раз вырастет время при блоке 1 байт, если файл увеличить вдвое.
3. Сколько вызовов `write` сделает сама программа `wcstat` (она печатает две строки), если её вывод идёт на терминал и если в файл. Опирайтесь на «Буферизацию `printf`».
4. Для команды с ошибкой: какой код `errno` из списка в «Теоретических сведениях» вы ожидаете и почему. Опирайтесь на `ls -ld` пути, который в ней используется, и на смысл операции.

**Эксперимент.**
1. Соберите программу, создайте `data.txt`, сверьте её результат с `wc` (три числа должны совпасть).
2. Серия `time ./wcstat -b <блок> data.txt` для пяти блоков варианта; для каждого — число блоков, `real`, `sys`.
3. Число вызовов `pread64` по `strace -c -e trace=pread64` для двух блоков из серии и для блока 1048576. Разность с числом блоков, которое напечатала программа, — не ошибка: найдите, откуда она.
4. Файл вдвое больше (`cat data.txt data.txt > data2.txt`): время при блоке 1 байт, сравнение с прогнозом.
5. Число вызовов `write` у `./wcstat data.txt` на терминал и с перенаправлением в файл (`strace -e trace=write`).
6. Команду с ошибкой выполните сначала без `strace` (сообщение и `echo $?`), затем под `strace -o trace.txt`. Найдите вызов, который вернул `-1`, отбросив ошибки запуска (`guide-04.md`, шаг 10). Запишите его строку, имя и число кода ошибки, условие из раздела ERRORS его справки.

**Анализ (ответы в отчёте).**
- Совпали ли числа вызовов с прогнозом **точно**? Если нет — найдите причину.
- Найдите блок, начиная с которого время почти перестаёт уменьшаться («колено»), и объясните, на что тратится время дальше.
- Оцените цену одного системного вызова: `sys` при блоке 1 ÷ число вызовов. Сколько это в микросекундах? Сколько вызовов в секунду способна обработать ваша машина?

- Сколько `write` сделала программа на терминал и в файл, и почему они различаются?
- Ошибка: какой вызов отказал и по какому условию ядро выбрало именно этот код? Совпал ли он с прогнозом? Чем код `errno` отличается от кода завершения команды (`echo $?`)? Что нужно изменить в условиях (путь, права, подготовка), чтобы этот вызов прошёл?
