# Лабораторная работа 6. Порядок выполнения

Вы проследите, как процессы передают данные через канал, и выясните, почему программа может ждать, хотя данные уже обработаны.

Работайте в одном терминале ВМ от обычного пользователя. Обозначения `<K>`, `<R>`, `<PID>` заменяйте своими числами, без скобок. Из [задания](task-06.md) выпишите число потомков `K` и размер записи `R`. PID и номера каналов у вас будут другими.

# Часть 1. Наблюдение

Эта часть входит в отчёт по лабораторной, но не в РГР.

## Шаг 1. Найдите открытые файлы процесса

**Файловый дескриптор** — номер открытого файла у процесса. Обычно 0 — ввод, 1 — вывод, 2 — вывод ошибок. Подробнее — лекция 6, раздел 6.2.

```bash
ls -l /proc/self/fd
ls -l /proc/self/fd < /etc/hostname
```

`/proc/self` здесь относится к самой команде `ls`. В первом выводе номера 0, 1 и 2 обычно указывают на терминал: `/dev/pts/...` или `/dev/tty...`.

Во втором опыте найдите номер 0: теперь он указывает на `/etc/hostname`. Оболочка перенаправила ввод до запуска `ls`. Дескриптор 3 может указывать на каталог `/proc/.../fd`, который сама `ls` открыла для просмотра.

📷 Сохраните оба вывода и подпишите, что изменилось.

## Шаг 2. Найдите каналы между тремя командами

Запустите конвейер:

```bash
sleep 300 | sort | wc -l &
sleep 1
ps -o pid,ppid,comm --ppid $$
```

В списке найдите PID трёх команд: `sleep`, `sort`, `wc`. Для каждой посмотрите открытые файлы, подставляя её PID:

```bash
ls -l /proc/<PID_sleep>/fd
ls -l /proc/<PID_sort>/fd
ls -l /proc/<PID_wc>/fd
```

Ищите ссылки вида `pipe:[номер]`. Одинаковые номера обозначают один канал. Ожидаемая связь:

```text
sleep: вывод 1 → канал A → ввод 0: sort
sort:  вывод 1 → канал B → ввод 0: wc
```

Номера A и B возьмите из своего вывода. `sleep` ничего не передаёт, но держит канал открытым; остальные команды ждут.

📷 Сохраните дескрипторы трёх процессов и нарисуйте схему соединений. Затем завершите именно этот `sleep`:

```bash
kill -TERM <PID_sleep>
```

После закрытия каналов `sort` и `wc` тоже должны завершиться.

**Если не получилось:** не нашли процессы — повторите запуск и смотрите список сразу. Не используйте PID из примера и не завершайте другие процессы `sleep` в системе.

## Шаг 3. Посмотрите, что происходит без читателя

```bash
yes | head -3
echo ${PIPESTATUS[@]}
seq 100 | head -1
echo ${PIPESTATUS[@]}
```

`PIPESTATUS` хранит результаты команд последнего конвейера. Читайте его сразу после конвейера: следующая команда изменит эти значения.

Обычно первый опыт даёт `141 0`: `head` получил строки и завершился, а следующая запись `yes` вызвала `SIGPIPE`. Число 141 — это 128 + 13, где 13 — номер сигнала.

Во втором опыте `seq` может успеть передать все данные и завершиться нормально: тогда результат `0 0`. При другом чередовании процессов возможен `SIGPIPE` и здесь. Запишите именно свой результат.

📷 Сохраните оба конвейера и их коды. Объясните, почему маленькая передача не обязана приводить к `SIGPIPE`.

**Проверьте часть 1.** Вы находите ввод и вывод процесса, соединяете процессы по номерам каналов и объясняете код 141. При затруднении повторите шаги 1–3.

# Часть 2. Исследование: канал между родителем и потомками

**Часть 2 этой лабораторной позже станет разделом 3 РГР. Повторно выполнять её не нужно.** Используйте `wcstat` и `data.txt` из ЛР 4.

Режим `-p K -c`: потомки считают свои части файла и после каждого блока отправляют родителю запись с результатом. Родитель читает записи из канала и складывает числа.

## Шаг 4. Запишите прогноз и проверьте обычный запуск

```bash
cd ~/<фамилия>/rgr/programs
ls -l wcstat data.txt
wc data.txt
```

Нет программы — выполните `make`. Нет файла — создайте по [гайду ЛР 4](../lab-04-syscalls/guide-04.md), шаг 6, со своим `N`.

**До запуска** запишите прогноз:

1. Какой итог получит родитель и сколько записей придёт. Для каждой из `K` частей разделите её длину на 4096, округлите вверх и сложите результаты. Части по размеру отличаются не более чем на байт.
2. Как будут соединены родитель и потомки; какие концы канала нужны каждому.
3. Что произойдёт, если родитель оставит открытым свой конец для записи.
4. Сколько записей размера `R` поместится в канал модели из задания: 16 страниц по 4096 байт, запись целиком помещается в одну страницу.

Теперь выполните:

```bash
./wcstat -p <K> -c data.txt
```

Итог по строкам, словам и байтам должен совпасть с `wc`. Сравните число полученных записей с прогнозом. Оно может быть немного больше числа блоков для файла целиком: у каждой части есть свой последний неполный блок.

📷 Сохраните итог программы и `wc`.

## Шаг 5. Рассмотрите оба конца канала

```bash
./wcstat -p <K> -c -b 4096 -s 100 data.txt > channel.txt &
P=$!
sleep 1
ls -l /proc/$P/fd
ps -o pid,ppid,comm --ppid $P
```

`P` хранит PID родителя. Из списка потомков выберите один PID:

```bash
C=<PID>
ls -l /proc/$C/fd
wait $P
```

У родителя ищите читающий конец (`r`), у потомка — пишущий (`w`) с тем же `pipe:[номер]`. Номера дескрипторов могут отличаться от примера: важны направление и общий номер канала.

📷 Сохраните оба списка и отметьте нужные строки.

**Если не получилось:** процесс уже закончился — повторите с `-s 500`. Пауза после блока даёт время заглянуть в `/proc`.

## Шаг 6. Оставьте лишний конец открытым

Ключ `-l` намеренно включает ошибку: родитель сохраняет свой конец канала для записи.

```bash
./wcstat -p <K> -c -l -b 4096 -s 100 data.txt > leak.txt &
P=$!
sleep 10
ps -o pid,stat,wchan:20,cmd -p $P
ps -o pid,stat,cmd --ppid $P
ls -l /proc/$P/fd
```

Посмотрите, завершились ли потомки. Если они ещё считают, подождите дольше. Когда они закончили, родитель всё ещё может спать в `pipe_read` или `anon_pipe_read`: он ждёт новые данные. В его списке остались **оба** конца одного канала.

Конец данных приходит, только когда закрыты все пишущие концы. Сам родитель не даёт этому условию выполниться. Поэтому правильные подсчитанные числа ещё не означают, что программа завершится.

📷 Сохраните состояние родителя, потомков и открытые дескрипторы. Остановите опыт:

```bash
kill -TERM $P
wait $P
echo $?
cat leak.txt
```

Ненулевой код после остановки ожидаем: программу прервали.

## Шаг 7. Заставьте писателя ждать свободного места

Размер блока файла и размер записи канала — разные вещи: `-b 512` задаёт порцию чтения, `-r R` — число байт одной записи в канале. Ключ `-d` откладывает чтение родителем.

Сначала измерьте число завершённых записей за три секунды:

```bash
timeout 3 strace -f -e trace=write -o writes.txt ./wcstat -p 1 -c -b 512 -r <R> -d 60 data.txt > /dev/null
echo $?
```

Код 124 означает, что `timeout` остановил опыт по времени. В следующей команде замените **оба** `<R>` одним числом своего варианта:

```bash
grep -c ', <R>) *= <R>' writes.txt
```

Например, для `R = 48` шаблон будет `', 48) *= 48'`. Он считает строки успешных записей по 48 байт.

Затем посмотрите состояние писателя:

```bash
./wcstat -p 1 -c -b 512 -r <R> -d 30 data.txt > capacity.txt &
P=$!
sleep 2
ps -o pid,stat,wchan:20,cmd --ppid $P
kill -TERM $P
wait $P
```

В `WCHAN` ищите `pipe_write` или `anon_pipe_write`: писатель спит, потому что места нет, а родитель пока не читает.

Для расчёта из задания сначала определите, сколько целых записей помещается в страницу: разделите 4096 на `R` и отбросьте остаток. Затем умножьте на 16. Например, при `R = 48`: 85 записей на страницу, всего 1360. Остатки страниц не вмещают ещё одну целую запись.

📷 Запишите измерение, расчёт и состояние потомка. Если число отличается, проверьте размер записи и список `writes.txt`: ёмкость канала зависит от настроек ядра, а незавершённый вызов может быть записан отдельно. Не меняйте результат ради совпадения с примером.

## Типичные ошибки

| Что произошло | Что сделать |
|---|---|
| Не найдена `wcstat` | Перейдите в `rgr/programs` и выполните `make` |
| Нет `data.txt` | Восстановите по шагу 6 гайда ЛР 4 |
| В команде остались скобки `<...>` | Замените обозначения своими числами |
| Пропал каталог `/proc/PID/fd` | Процесс завершился; повторите с большей паузой |
| Слишком много записей по сравнению с целым файлом | Учитывайте неполный блок каждой части, а не только всего файла |
| Запуск с `-l` не завершается | Это ожидаемый опыт; завершите родителя через `kill -TERM $P` |
| `WCHAN` называется иначе или показан `-` | Запишите состояние и дескрипторы; имя зависит от системы |
| `grep` насчитал 0 записей | Замените оба размера в шаблоне и откройте `writes.txt` |
| Канал не заполнился | Проверьте `-b 512`, размер записи и достаточность данных |
| Код `PIPESTATUS` неожиданный | Читайте его сразу после конвейера; порядок выполнения влияет на результат |
