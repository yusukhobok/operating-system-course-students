# Лабораторная работа 8. Порядок выполнения

Вы найдёте потоки процесса, сравните их работу и проверите, что происходит, когда несколько потоков изменяют общие данные. Затем включите защиту мьютексом и измерите её влияние.

Команды выполняйте в одном терминале ВМ без `sudo`. Обозначения `<...>` заменяйте своими значениями. Из [задания](task-08.md) выпишите `N` — число строк большого файла, `b` — размер блока и `T` — число потоков. Время и ошибки подсчёта у вас не обязаны совпасть с чужим примером.

# Часть 1. Наблюдение

Эта часть входит только в отчёт по лабораторной.

## Шаг 1. Соберите программу и проверьте число процессоров

```bash
cd ~/<фамилия>/lab08/programs
make
nproc
```

После сборки должна появиться программа `threads`. Она создаёт четыре рабочих потока. `nproc` показывает число доступных процессоров.

**Поток** выполняет команды внутри процесса. Потоки одного процесса используют общую память, но каждый имеет свои регистры и стек. Подробнее — лекция 7, разделы 7.1–7.3.

Если доступен один процессор, потоки будут работать по очереди. Это не мешает наблюдению, но влияет на ускорение и проявление гонки. Запишите число процессоров в отчёт.

**Если не получилось:** нет папки или компилятора — проверьте шаги 4–5 [инструкции настройки ВМ](../../handouts/vm-setup.md): пакеты из `ospkgs.iso` и материалы из `oslabs.iso`.

## Шаг 2. Найдите потоки в системе

```bash
ps -e | wc -l
ps -eL | wc -l
./threads > sleeping.txt &
P=$!
sleep 1
ps -L -o pid,lwp,stat,pcpu,comm -p $P
ls /proc/$P/task
grep Threads /proc/$P/status
```

`P=$!` сохраняет PID фоновой программы. `ps -e` показывает процессы, `ps -eL` — отдельные потоки. Оба счётчика включают строку заголовка, поэтому сравнивайте их с этой оговоркой.

У `threads` ожидайте пять потоков: четыре рабочих и главный. В `ps -L`:

- `PID` у них общий;
- `LWP` — номер отдельного потока;
- у главного потока `LWP` совпадает с `PID`;
- состояние `S` означает ожидание: в этом режиме рабочие потоки спят.

Сравните число строк с каталогами в `/proc/$P/task` и полем `Threads`.

📷 Сохраните три способа наблюдения потоков. Завершите этот запуск:

```bash
kill -TERM $P
wait $P
```

## Шаг 3. Посмотрите работающие потоки

```bash
./threads busy > busy.txt &
P=$!
sleep 3
ps -L -o pid,lwp,stat,pcpu,comm -p $P
wait $P
cat busy.txt
```

Рабочие потоки около 30 секунд выполняют вычисления. Ищите у них `R` и ненулевую загрузку CPU; главный поток ждёт их завершения.

Программа печатает два времени: сколько прошло по часам и сколько процессорного времени суммарно использовали потоки. При четырёх доступных процессорах четыре потока могут за 30 секунд по часам получить около 120 секунд процессорного времени. При меньшем числе процессоров сумма будет меньше.

📷 Сохраните `ps -L` и итог программы. Объясните различие двух времён.

**Если не получилось:** в `/proc` уже нет процесса — повторите и посмотрите раньше. Нагрузка каждого потока меньше 100 % — проверьте число процессоров и конкурирующую нагрузку ВМ.

**Проверьте часть 1.** Вы различаете PID процесса и номера потоков, находите главный поток и объясняете, почему процессорное время может быть больше времени по часам.

# Часть 2. Исследование: общие данные и мьютекс

**Эта часть позже станет разделом 5 РГР. Повторять опыты не нужно.** Здесь используется другая программа: `wcstat` в `rgr/programs`.

В режиме `-t T` потоки считают части файла и обновляют общий итог. Без защиты в программе намеренно оставлена ошибка. Ключ `-x` защищает обновление **мьютексом**: пока один поток работает с общими данными, остальные ждут. Подробнее — лекция 8, разделы 8.1 и 8.3.

## Шаг 4. Создайте файл и получите правильный результат

```bash
cd ~/<фамилия>/rgr/programs
make
seq 1 <N> | sed 's/$/ alpha beta gamma/' > big.txt
ls -l big.txt
wc big.txt
./wcstat -t 1 -b <b> big.txt
```

`seq` создаёт числа по одному на строку, `sed` дописывает три слова. Файл `big.txt` сохраните: он понадобится в ЛР 10.

Результат одного потока должен совпасть с `wc`. Строка «для сравнения (один поток)» — контрольный подсчёт самой программы. «Потеряно» — разность между контрольным и общим итогом.

**До серий запусков** запишите прогноз: правильность и время при 1, 2, `T`, `2T` потоках; влияние `-x`; работа на одном CPU; различие числа `futex` с защитой и без неё. Для `2T` заранее вычислите число: например, при `T = 3` это 6.

📷 Сохраните эталон, размер файла и число процессоров.

**Если не получилось:** не совпал даже один поток — проверьте файл, сборку и сообщения об ошибках. Не переходите к сравнению, пока не получили эталон.

## Шаг 5. Измерьте работу без защиты

Выполните три запуска: с 2, своим `T` и удвоенным числом `2T` потоков:

```bash
./wcstat -t 2 -b <b> big.txt
./wcstat -t <T> -b <b> big.txt
./wcstat -t <2T> -b <b> big.txt
```

В `<2T>` подставьте уже вычисленное число, а не выражение `2T`. Подготовьте таблицу:

| Потоков | Мьютекс | Потеряно строк | Потеряно слов | Потеряно байт | Время, с |
|---|---|---|---|---|---|
| 1 | нет | | | | |
| 2 | нет | | | | |
| ваш `T` | нет | | | | |
| ваше `2T` | нет | | | | |

Чтобы представить причину ошибки, разложите обновление на чтение старого значения, прибавление и запись. Два потока могут прочитать одно старое значение, а затем один затрёт результат другого.

Это учебная модель гонки, а не гарантия трёх машинных команд. В C несогласованные обращения такого рода дают неопределённое поведение. Поэтому у неисправной программы нельзя обещать точный размер или обязательный рост потерь. Записывайте наблюдения и сравнивайте повторные запуски.

📷 Сохраните результаты и заполните таблицу. Не делайте вывод об исправности по одному удачному запуску.

## Шаг 6. Включите мьютекс

Повторите серию с `-x`, включая один поток:

```bash
./wcstat -t 1 -x -b <b> big.txt
./wcstat -t 2 -x -b <b> big.txt
./wcstat -t <T> -x -b <b> big.txt
./wcstat -t <2T> -x -b <b> big.txt
```

Добавьте строки в ту же таблицу. При успешной обработке файла с мьютексом итог должен совпадать с эталоном. Сравните время для одинакового числа потоков с защитой и без неё, а также с одним потоком.

Мьютекс заставляет выполнять защищённый участок по одному. Поэтому больше потоков не обязательно означает быстрее: они могут тратить время на ожидание друг друга.

📷 Сохраните серию и вычислите отношение времён для своего `T`.

**Если не получилось:** с `-x` итог неверен — проверьте наличие ключа, имя файла и ошибки программы. Не списывайте неверный защищённый результат на случайность.

## Шаг 7. Оставьте один CPU и посмотрите `futex`

```bash
taskset -c 0 ./wcstat -t <T> -b <b> big.txt
taskset -c 0 ./wcstat -t <T> -x -b <b> big.txt
```

`taskset -c 0` разрешает программе использовать только CPU 0. Потоки продолжают существовать, но выполняются по очереди. Сравните правильность и время. Один CPU сам по себе не исправляет несогласованную работу с общими данными.

Теперь посчитайте вызовы `futex`:

```bash
strace -f -c -e trace=futex -o mutex.txt ./wcstat -t <T> -x -b <b> big.txt > /dev/null
cat mutex.txt
strace -f -c -e trace=futex -o unprotected.txt ./wcstat -t <T> -b <b> big.txt > /dev/null
cat unprotected.txt
```

`-f` включает наблюдение за потоками, `-c` считает вызовы. `futex` помогает потокам ждать и просыпаться. Он используется не только мьютексами, но и, например, ожиданием завершения потока. Поэтому без `-x` его число не обязано быть нулевым или всегда равным одному.

Захват свободного мьютекса может обойтись без системного вызова. Не приравнивайте число `futex` к числу захватов. Время этих запусков не используйте для обычного сравнения скорости: `strace` замедляет программу.

📷 Добавьте два опыта на одном CPU и обе сводки в отчёт.

**Если не получилось:** нет `taskset` — проверьте пакеты из `ospkgs.iso`. Если CPU 0 недоступен, посмотрите разрешённые CPU командой `taskset -pc $$`, выберите один и укажите его в отчёте.

**Проверьте исследование.** Есть эталон, две серии с одинаковыми числами потоков, один CPU и две сводки `futex`.

## Типичные ошибки

| Что произошло | Что сделать |
|---|---|
| Не найдена программа `threads` | Соберите её в `lab08/programs` |
| Не найдена `wcstat` | Перейдите в `rgr/programs` и выполните `make` |
| Потеряли PID фонового опыта | Сохраняйте `P=$!` сразу после запуска |
| В `ps` пять потоков вместо четырёх | Учтите главный поток вместе с рабочими |
| Потоки получают меньше 100 % CPU | Сравните их число с `nproc` и нагрузкой ВМ |
| Нет потерь без защиты | Повторите, проверьте свой `N` и `b`; удачный запуск не доказывает корректность |
| С мьютексом стало медленнее | Запишите измерение и объясните ожидание на общем участке |
| `-t` вне диапазона 1–16 | Проверьте `T` и заранее вычислите `2T` |
| `taskset` не принимает CPU 0 | Выберите доступный CPU по `taskset -pc $$` |
| Число `futex` отличается от примера | Сравнивайте режимы, не требуйте фиксированного числа |
